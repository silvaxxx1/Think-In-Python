§ 01 · Foundations

A computer is three things
talking to each other.

Strip away the marketing, the operating systems, the package managers — and a computer is a profoundly simple idea.

Every machine you've ever programmed reduces to the same three components: a thing that does math, a thing that stores numbers, and wires that move numbers between them. That's the entire abstraction. The CPU computes. The memory holds bits. The bus shuttles them around. Add a GPU and an SSD and a network card, and you have not added new categories — you have added new instances of the same three things.

For an ML engineer this is recognisable: when training feels slow you instinctively ask "am I compute-bound or memory-bound?" — and the answer always lives in this triangle. Either the math is the bottleneck (compute) or the data movement is (memory and buses). Almost nothing else can be slow.

§ 02 · Compute

The CPU has been stuck
for twenty years.

Clock speeds peaked around 2005. Since then, "faster" has meant something completely different — and understanding what changed explains most of modern software performance.

A CPU's speed used to be a single number: clock speed, the number of cycles per second. Cycle faster, compute faster. Simple. From the 80s to the early 2000s clock speeds doubled roughly every two years, and code got faster for free.

Then physics caught up. Making transistors smaller and switching them faster started cooking the chip. Around the 4 GHz mark, the industry hit a thermal wall. Clock speeds stopped going up. You can still buy a 5 GHz consumer chip in 2026 — but you could buy a 3.8 GHz Pentium 4 in 2004. That's twenty years of stagnation in the headline number.

So how do modern CPUs get faster?

Three tricks, all of which matter to your code:

01. Instructions per cycle (IPC)

A modern CPU does more per cycle — pipelining, branch prediction, speculative execution. Same clock speed, more work. This is invisible to your code but real.

02. SIMD — single instruction, multiple data

The CPU has special instructions that operate on 8 or 16 numbers at once. Add eight floats in one instruction, multiply eight pairs in one instruction. This is vectorization, and it is the single most important hardware feature for numerical computing. numpy exists because of this. torch exists because of this. A Python for loop cannot use SIMD. A vectorized NumPy operation can.

03. Multi-core

Instead of one fast core, ship eight medium ones. Your laptop has 8–16 cores; a server has 64–128. This is great if your problem can be split across them. Most can't, fully.

Amdahl's Law, in plain English: if 10% of your program runs serially (can't be parallelized), the maximum speedup from infinite cores is 10×. Not 100×, not 1000× — 10×. The serial slice is the ceiling. This is why a DataLoader with 16 workers doesn't make training 16× faster.

Why GPUs feel like magic

A CPU has 8–16 powerful cores. A GPU has thousands of weak ones. For matrix multiplication — which is parallelizable to an almost absurd degree — the GPU wins by orders of magnitude. But there's a catch: the GPU sits on the PCIe bus, far from main memory. Getting data to the GPU is slow. This is why you batch, why you keep tensors on-device, why .cpu() in a hot loop is a known footgun.

§ 03 · Memory

Fast and big are enemies.

No memory technology gives you both speed and capacity. So computers stack memory in tiers and gamble that the next byte you need is already in a fast tier.

The trade-off is physical. Fast memory is built from transistors arranged for speed (SRAM) — expensive per bit, generates heat, lives on the CPU die itself. Cheap memory is built differently (DRAM, NAND flash, spinning rust) — more bits per dollar, but the read takes longer. You cannot have both.

The clever solution: a hierarchy. Tiny amount of ultra-fast memory closest to the CPU. A bit more, slightly slower, next out. A lot more, much slower, further out. The CPU automatically copies hot data inward, betting that you'll use the same bytes again soon. When that bet pays off — a cache hit — your code flies. When it doesn't — a cache miss — you wait.

A cache miss to RAM is 100× slower. A disk access is 100,000× slower. Optimize for locality, or accept the tax.

Sequential vs random access

Here's the second crucial property: memory is faster when you read it in order. Reading 1 MB sequentially is dramatically faster than reading 1 MB scattered across the address space. This is why a NumPy array crushes a Python list of numbers — the array is one contiguous slab of bytes, the list is a thousand pointers to a thousand integer objects scattered all over RAM.

The CPU prefetches. When you read byte N, it speculatively grabs N+1, N+2, ... N+64 (a "cache line") on the assumption you'll want them next. If your data is laid out sequentially, this works perfectly. If you're hopping around, the prefetcher is wrong every time, and you eat the full RAM latency on every access.

What this means for your code

# A Python list of a million ints
data = [i for i in range(1_000_000)]
# 1M pointers, scattered. Every sum() walks the heap.
# Each int is a separate PyObject with refcount, type, value.

# A NumPy array of the same numbers
data = np.arange(1_000_000)
# One contiguous 8MB block. The CPU prefetches perfectly.
# Sequential SIMD math at full memory bandwidth.

# Identical result. ~100x speed difference.
§ 04 · Wires

Everything is connected
by a bus.

A bus is just a bundle of wires. Its speed is a function of how many wires (width) and how fast they switch (frequency). Every connection in your machine is a bus, and they vary wildly.

Here's a partial map of the buses inside a typical workstation, in rough order of speed:

Notice something: the GPU's own memory is faster than the CPU's, but the path between CPU and GPU is the narrow part. This is the entire ML systems story. You don't move data between CPU and GPU in a training loop. You move it once at startup, then keep it on-device and feed it the same way every batch. Crossing PCIe is the single most expensive thing your code can do, per byte.

§ 05 · Python

Python pays two taxes
that compiled languages don't.

Python is wonderful for development speed and devastating for raw performance. Understanding exactly why turns the language from an obstacle into a tool you can work around.

Tax #1: Everything is an object

In C, an int is 8 bytes. Just the number. In Python, an int is a PyObject — about 28 bytes — with a type pointer, a reference count, and the value. A list of integers in Python isn't a contiguous block of integers. It's a contiguous block of pointers, each pointing to a separately allocated integer object somewhere in the heap.

This destroys cache locality. When you iterate through a Python list of a million ints, every access is a potential cache miss because the actual integer values are scattered all over memory. Your CPU's beautiful prefetcher is useless.

This is the entire reason NumPy, PyTorch, and JAX exist. They side-step Python's object model by storing raw bytes in C-managed arrays. When you call tensor.sum(), Python hands control to a C function that operates on contiguous memory using SIMD instructions. Python is just orchestrating; the work happens in a sane memory layout.

Tax #2: The GIL

The Global Interpreter Lock is a mutex that allows only one Python instruction to execute at a time, no matter how many cores your machine has. You can spawn 16 threads on a 16-core CPU and they will take turns, not run in parallel. For CPU-bound Python code, threading gives you zero speedup.

GIL: one Python instruction at a time

The GIL exists for good reasons (it makes the CPython implementation dramatically simpler, especially around reference counting), but it's the reason Python parallelism is hard.

How everyone works around the GIL

Four established escape hatches, in increasing order of effort:

1. Release the GIL in C code

NumPy, PyTorch, and friends release the GIL before doing heavy work in their C/CUDA kernels. This is why ML in Python is fast at all. Your Python interpreter is just dispatching; the actual work runs in compiled code with no lock. torch.matmul(A, B) happily uses all cores and the entire GPU.

2. multiprocessing

Spawn separate Python processes instead of threads. Each process has its own GIL, so they really run in parallel. The catch: passing data between processes requires serialization (pickling), which is slow. Good for embarrassingly parallel batches; bad for fine-grained sharing.

3. async / await

Doesn't help with CPU work — but excellent for I/O-bound workloads. While one coroutine waits on a network response, others run on the same thread. The GIL doesn't matter because nothing is CPU-busy.

4. Drop to C / Cython / Rust

For hot loops that NumPy can't vectorize, write the inner loop in C, Cython, or a Rust extension. Tools like numba JIT-compile a subset of Python to machine code, including releasing the GIL.

Note on Python 3.13+: there's now an experimental free-threaded build that removes the GIL entirely. It's a multi-year transition, and most C extensions aren't yet thread-safe under it. But the era of the GIL is, slowly, ending.
§ 06 · Playbook

A performance playbook
for ML engineers.

Everything above, distilled into actions. Run through these top-down when something is slower than you think it should be.

01

Profile before you optimize

Never guess. Use cProfile, py-spy, torch.profiler, or nvidia-smi. The bottleneck is rarely where you think — and "obvious" optimizations to non-bottlenecks are wasted effort.

02

Pick a better algorithm first

O(n²) → O(n log n) beats every hardware trick. A sorted lookup, a hash map, a smarter loss, a sparse representation — these dwarf cache optimizations. Don't micro-optimize a bad algorithm.

03

Vectorize ruthlessly

Replace Python for loops with NumPy/PyTorch operations. Vectorized code uses SIMD, releases the GIL, and processes contiguous memory. A 100× speedup from this single change is normal.

04

Keep memory contiguous

Prefer arrays over lists of objects. Use tensor.contiguous() when an op needs it. Avoid creating tiny temporary tensors in a hot loop. Cache locality is invisible but real.

05

Minimize device transfers

Every .cpu(), .cuda(), .numpy(), or .item() crosses the PCIe bus. In a training loop these add up to dominate everything else. Move data once, keep it on-device.

06

Batch your work

Bus transfers have fixed overhead per call. One batch of 1024 is dramatically cheaper than 1024 batches of one. This applies to GPU calls, DB queries, network requests, and disk reads alike.

07

Overlap compute and I/O

While the GPU trains step N, the DataLoader should be preparing step N+1 on CPU workers. PyTorch's num_workers, pin_memory, and prefetch_factor exist for exactly this.

08

For CPU parallelism, use processes not threads

multiprocessing, joblib, or just sharding work across separate Python processes. Threads will not help with CPU-bound Python work because of the GIL.

09

Drop down when you have to

For genuinely hot Python loops that can't be vectorized, reach for numba, cython, or a C/Rust extension. These compile to native code and bypass the interpreter entirely.
